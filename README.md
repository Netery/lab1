# StudyTracker — лабораторна робота №1

**Курс:** Технології створення програмних продуктів
**Виконав:** Заболотний Артем, група К-41

StudyTracker — веб-застосунок для обліку навчальних завдань, дедлайнів і прогресу студента.
Цей репозиторій містить технічне завдання, політику версіонування та шаблони для командної роботи.

## Структура репозиторію

| Файл | Призначення |
|---|---|
| `ТЗ.md` | Технічне завдання на StudyTracker |
| `VERSIONING.md` | Політика версіонування (SemVer + спрощений GitFlow) |
| `RELEASE_TEMPLATE.md` | Шаблон release notes |
| `CHANGELOG.md` | Історія змін у форматі Keep a Changelog |
| `ACCEPTANCE_CHECKLIST.md` | Чекліст приймання фічі |

## Як перевірити

1. Склонувати репозиторій: `git clone <url>`
2. Переглянути гілки: `git branch -a`
3. Переглянути історію з гілками: `git log --oneline --graph --all`
4. Переглянути теги релізів: `git tag` і `git show v1.0.0`

## Вибір моделі життєвого циклу

Для проєкту обрано **Agile (Scrum)** зі спринтами тривалістю 1 тиждень.

StudyTracker — невеликий проєкт, вимоги до якого уточнюються в процесі: після перших версій користувачі (студенти) можуть попросити нові функції, наприклад нагадування чи статистику. Scrum дозволяє випускати робочу версію після кожного спринту, швидко отримувати зворотний зв'язок і змінювати пріоритети без переписування всього плану. Waterfall тут менш доречний, бо він вимагає зафіксувати всі вимоги на початку, а зміни на пізніх етапах дорогі.

**Артефакти:**
- *Product Backlog* — список усіх функцій з пріоритетами (з розділу 4 ТЗ);
- *Sprint Backlog* — задачі, взяті в поточний спринт;
- *Definition of Done* — фіча вважається готовою, коли виконано всі пункти `ACCEPTANCE_CHECKLIST.md`.

**Розклад ітерацій:**
- Sprint Planning — понеділок, вибір задач на тиждень;
- Daily — коротка перевірка прогресу (для 1 розробника — запис у трекері);
- Sprint Review — п'ятниця, демонстрація результату;
- Retrospective — п'ятниця, що покращити в наступному спринті.

**Ризики:** нечіткі вимоги можуть розтягнути беклог, а при одному розробнику складно дотримуватися всіх церемоній. Щоб зменшити ці ризики, беклог обмежено обсягом MVP, а церемонії спрощено.

Оскільки команда складається з 1 людини, використовується **спрощений GitFlow** без гілок `release/*` (див. `VERSIONING.md`).
