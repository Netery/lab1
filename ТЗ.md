# Технічне завдання: StudyTracker

## 1. Вступ
StudyTracker — веб-застосунок, у якому студент веде список навчальних завдань з дедлайнами, позначає їх виконання та бачить, що потрібно здати найближчим часом.

## 2. Мета і задачі
- **Мета:** допомогти студенту не пропускати дедлайни та планувати навчання.
- **Основні задачі:**
  - зберігати завдання з предметом, описом і дедлайном;
  - показувати найближчі та прострочені завдання;
  - відстежувати прогрес виконання.

## 3. Цільова аудиторія
Студенти коледжів і університетів.

**Ключові сценарії:**
- студент додає нове завдання після пари;
- студент відкриває застосунок і бачить, що здати на цьому тижні;
- студент позначає завдання як виконане.

## 4. Функціональні вимоги
1. **Реєстрація та вхід** — користувач створює акаунт за email і паролем.
   *Критерії приймання:* після реєстрації можна увійти; з неправильним паролем вхід неможливий.
2. **Додавання завдання** — поля: назва, предмет, опис, дедлайн.
   *Критерії приймання:* завдання з'являється у списку; без назви або дедлайну збереження неможливе.
3. **Редагування та видалення завдання.**
   *Критерії приймання:* зміни зберігаються; видалене завдання зникає зі списку.
4. **Позначення завдання виконаним.**
   *Критерії приймання:* виконане завдання відображається окремо і не потрапляє в список «найближчих».
5. **Список найближчих дедлайнів** — сортування за датою, прострочені виділені червоним.
   *Критерії приймання:* завдання впорядковані за дедлайном; прострочені позначені.
6. **Фільтр за предметом.**
   *Критерії приймання:* при виборі предмета показуються лише його завдання.

## 5. Нефункціональні вимоги
- **Продуктивність:** час відповіді сервера < 500 ms для списку до 500 завдань.
- **Безпека:** паролі зберігаються у вигляді хешу (bcrypt), доступ до завдань лише після входу.
- **Сумісність:** останні версії Chrome, Firefox, Edge; адаптивний інтерфейс для смартфонів.
- **Логування/моніторинг:** запис помилок сервера у лог-файл.

## 6. Обмеження та припущення
- Технології: Python 3.11, Flask, SQLite, HTML/CSS (Bootstrap).
- Розробник — 1 людина, термін розробки MVP — 3 тижні.
- Застосунок працює онлайн, офлайн-режим не передбачено.

## 7. Інтерфейс користувача (коротко)
- **Сторінка входу/реєстрації** → після входу перехід на головну.
- **Головна:** список найближчих завдань, кнопка «Додати завдання», фільтр за предметом.
- **Форма завдання:** назва, предмет, опис, дедлайн, кнопки «Зберегти» / «Скасувати».
- **Архів:** виконані завдання.

## 8. Архітектурні рішення (високорівневі)
- **Сервер:** Flask-застосунок (шаблони Jinja2).
- **БД:** SQLite (таблиці `users`, `tasks`).
- **Контроль версій:** Git + GitHub, спрощений GitFlow.
- **CI/CD:** GitHub Actions — запуск тестів при кожному push у `develop` і `main`.
- **Деплой:** хостинг Render або PythonAnywhere з гілки `main`.

## 9. План робіт та етапи
- **Ітерація 1 (тиждень 1):** реєстрація, вхід, структура БД.
- **Ітерація 2 (тиждень 2):** додавання, редагування, видалення завдань.
- **Ітерація 3 (тиждень 3):** найближчі дедлайни, фільтр, архів виконаних.
- **Реліз 1.0.0:** MVP з усіма функціями розділу 4.

## 10. Критерії приймання
- Усі функціональні вимоги з розділу 4 виконуються.
- Тест-кейси:
  1. Реєстрація нового користувача → успішний вхід.
  2. Вхід з неправильним паролем → повідомлення про помилку.
  3. Додавання завдання без дедлайну → помилка валідації.
  4. Завдання з минулим дедлайном → виділене червоним.
  5. Позначення виконаним → завдання переходить в архів.
- Пройдено всі пункти `ACCEPTANCE_CHECKLIST.md`.

## 11. Додатки
- Схема БД: `users(id, email, password_hash)`, `tasks(id, user_id, title, subject, description, deadline, is_done)`.
